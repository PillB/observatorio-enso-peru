# 2. Solarize execution method

For each major phase:

## 2.1 Research

1. Query previous research, source, decision, test, and failure ledgers.
2. Inspect the current repository and production behavior.
3. Revalidate official documentation and live endpoints.
4. Identify at least two realistic approaches for a material architectural
   decision.
5. Record:
   - VERIFIED
   - ASSUMED
   - UNRESOLVED
   - REJECTED
6. Define measurable acceptance criteria.
7. Stop after sufficient evidence is obtained.

Refresh research whenever:

- An endpoint changes.
- A source misses its expected publication window.
- A schema changes.
- A PDF layout changes.
- A dataset version changes.
- A climatology changes.
- A library or GitHub feature changes.
- A fix affects another subsystem.
- Actual performance contradicts the design.

Use at most three research–critique–revision rounds per material decision.

## 2.2 RED

Before implementation:

1. Reproduce the current failure.
2. Preserve evidence.
3. Write a failing test that expresses required behavior.
4. Verify that it fails for the expected reason.

## 2.3 GREEN

Implement the smallest complete correction.

Do not:

- Suppress failures.
- Replace observations with synthetic values.
- Hardcode current values or dates.
- Treat retrieval time as observation time.
- Substitute a scientifically different indicator.
- weaken assertions.
- Increase retries without diagnosis.
- Publish low-confidence document extraction.
- deploy a partial dataset.

## 2.4 REFACTOR

After Green:

- Remove duplication.
- Improve contracts.
- Improve comments and documentation.
- Optimize requests and asset sizes.
- Preserve verified numerical behavior.
- Rerun affected scientific, functional, workflow, and browser tests.

## 2.5 Independent verification

The implementer may not approve its own result.

Require an independent verifier to inspect the evidence, deployment identity,
data lineage, and live behavior.

Use no more than three remediation rounds.

Require two consecutive quiet live-production verification rounds before
declaring readiness.

# 4. Fundamental scientific architecture

Maintain three separate temporal layers.

## 4.1 Rapid observational layer

May update daily or weekly.

Examples:

- Daily gridded OISST.
- Daily Peruvian coastal SST products.
- Weekly Niño 1+2 and Niño 3.4.
- Weekly reports and observational summaries.
- Daily or higher-frequency buoy and reanalysis products when verified.

This layer reports observations and project-generated descriptive signals.

It must not independently change an official NOAA or ENFEN classification.

## 4.2 Operational index layer

Updates according to the source’s actual methodology.

Examples:

- ICEN and ICEN temporal.
- RONI.
- Monthly SOI.
- Three-month SOI.
- Monthly 850 hPa trade-wind indices.
- Validated D20 products.

Never create a higher-frequency value by averaging an incompatible faster
series unless the complete official methodology is reproducible and approved.

## 4.3 Official-authority layer

Contains only text or statuses explicitly published by the authority.

Examples:

- ENFEN official coastal status.
- NOAA/CPC official ENSO status.

Official status may remain unchanged while faster observations update.

Display its publication date and valid period.

- Expected dimensions exist.
- Values fall within plausible broad bounds.
- Latest period is compatible with the source cadence.

# 10. Fallback graph

Implement explicit, metric-compatible fallback levels.

Level 0:
Current primary authoritative structured source.

Level 1:
Scientifically equivalent authoritative source for the same metric,
aggregation, region, unit, and climatology.

Level 2:
Lower-cadence authoritative source for the same metric, clearly dated.

Level 3:
Last-known-valid historical observation, excluded from current status when
stale.

Level 4:
Metric unavailable.

Never silently substitute:

- Weekly Niño 1+2 for ICEN.
- Niño 3.4 for RONI.
- A point D20 value for a basin average.
- Surface wind for 850 hPa wind.
- An anomaly for actual wind.
- A project operational signal for an official classification.
- A narrative statement for an exact measurement.

Every fallback use must be displayed in health and provenance records.

# 12. Cross-source validation

For every accepted current observation:

- Compare against a second authoritative product when one exists.
- Calculate the difference using deterministic code.
- Define scientifically justified tolerance by metric.
- Investigate discrepancies outside tolerance.
- Retain both observations when they represent different products.
- Do not average incompatible sources merely to make them agree.

Examples:

- Compare derived daily Niño-region averages with published weekly CPC values
  over matching periods.
- Compare coastal OISST with IMARPE coastal products while preserving their
  different domains and methods.
- Compare GODAS subsurface interpretation with TAO observations when coverage
  permits.

indicator while preserving scientific compatibility.

automatically publishes new accepted information when available.

## Pre-simulation improvement rounds

**Round 1 — “newest” versus “official.”**  
The original follow-up risked replacing monthly official classifications with faster proxy observations. The revised prompt creates separate rapid-observation, operational-index, and official-authority layers.

**Round 2 — retries versus reliability.**  
“Perseverance” could have produced infinite retry loops and institutional load. The revised version uses conditional retrieval, per-host budgets, circuit breakers, finite recovery, and explicit unavailable states.

**Round 3 — daily run versus daily update.**  
The original wording treated execution as evidence of an update. The revised version distinguishes `NEW_RELEASE_ACCEPTED`, `NO_NEW_RELEASE`, `NOT_DUE`, revision, fallback, quarantine, and failure.

## Spirit-preservation verdict

**Passed.** The prompt preserves the demand for maximum research, newer data, layered fallbacks, autonomous daily operation, implementation, commits, deployment, and live validation. It now makes those goals scientifically compatible, bounded, auditable, and suitable for production rather than rewarding superficial timestamp refreshes or fragile scraping.
