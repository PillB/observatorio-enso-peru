# 2. Core evidence rules

A claim may be marked passed only when all applicable evidence layers exist:

1. Requirement evidence:
   The expected behavior is traceable to an approved requirement.

2. Implementation evidence:
   The responsible code, configuration, data contract, or workflow exists.

3. Test evidence:
   Relevant automated or manual tests were executed.

4. Artifact evidence:
   Generated data or build output has been inspected.

5. Deployment evidence:
   The intended artifact and commit reached GitHub Pages.

6. Live evidence:
   The expected behavior was observed on the production URL.

7. Independent-verifier evidence:
   A verifier other than the implementer confirmed the result.

Never treat the following as proof:

- README claims.
- Worklog claims.
- Code comments.
- Screenshots without metadata.
- Successful compilation alone.
- A green workflow label without job and artifact inspection.
- A test that was not executed.
- A test that passed only after unexplained retries.
- Mock data used by production.
- Synthetic observations presented as current.
- A new generation timestamp applied to unchanged observations.
- A local result used as proof of production behavior.

Every pass status must reference at least one retained evidence artifact.

# 4. Research protocol

Before each major phase or material defect:

1. Query existing project ledgers, prior tests, decisions, and failed
   hypotheses.
2. Inspect the current implementation.
3. Reproduce the live behavior when applicable.
4. Research current primary documentation for the relevant:
   - Scientific source.
   - API.
   - Data format.
   - Browser behavior.
   - Playwright capability.
   - Accessibility requirement.
   - GitHub Actions behavior.
   - Mapping or visualization library.
5. Produce at least two plausible causes for major defects.
6. Define tests capable of distinguishing those causes.
7. Record:
   - VERIFIED
   - ASSUMED
   - UNRESOLVED
   - REJECTED
8. Stop research when enough evidence exists to act.

Use no more than three research–critique–revision rounds per major decision.

# 8. Test-design protocol

For each deliverable, create tests in this order:

1. Happy path.
2. Boundary values.
3. Missing input.
4. Stale input.
5. Incompatible input.
6. Malformed input.
7. Source failure.
8. Browser failure.
9. Mobile state.
10. Accessibility state.
11. Adversarial state.
12. Regression state.

Before implementing a defect correction:

- Write a failing test.
- Execute it.
- Capture failure evidence.
- Confirm it fails for the intended reason.

Tests must assert user-visible or scientific behavior rather than mirror the
implementation.

A critical test that passes only after retry is `FLAKY`, not passed.

Do not use arbitrary sleeps. Wait for observable conditions.

# 12. Root-cause and fix selection

For every CRITICAL, HIGH, or MAJOR defect:

1. Produce at least two plausible causes.
2. Create discriminating tests.
3. Confirm one root cause or retain explicit uncertainty.
4. Search the codebase for the same pattern.
5. Map all affected components.
6. Compare at least two realistic fixes.
7. Assess:
   - Scientific correctness.
   - Data lineage.
   - Accessibility.
   - Browser compatibility.
   - Responsive impact.
   - Maintainability.
   - Performance.
   - Security.
   - Tutorial compatibility.
   - Chat compatibility.
   - Deployment risk.
8. Select the smallest complete correction.
9. Add regression tests.
10. Verify that related functionality does not regress.

Do not deploy multiple speculative alternatives sequentially to production.

Use isolated worktrees or branches for competing experiments.

# 13. Fix protocol

When authorized:

1. Preserve before evidence.
2. Add the failing Red test.
3. Confirm Red.
4. Implement the minimal Green correction.
5. Confirm targeted tests pass.
6. Refactor only after Green.
7. Run all impacted tests.
8. Run the critical full suite.
9. Update accurate documentation.
10. Create a coherent commit.
11. Push a remediation branch.
12. Open or update the pull request.
13. Pass required checks.
14. Obtain required review.
15. Merge according to repository policy.
16. Verify the Pages deployment.
17. Validate the live site.
18. Obtain independent verification.
19. Close the defect only as `VERIFIED_LIVE`.

Do not:

- Remove failing tests.
- Reduce assertions.
- Add arbitrary retries.
- Hardcode current values.
- replace real data with fixtures.
- hide a broken control.
- suppress workflow errors.
- use global overflow clipping as the only responsive fix.
- weaken CSP without a threat analysis.
- call a feature complete when only a UI shell exists.

# 16. Regression and independent verification

After every deployed remediation:

1. Use a fresh browser context.
2. Use a returning-user cached context.
3. Verify the deployed SHA.
4. Verify the publication ID.
5. Retest the corrected deliverables.
6. Retest adjacent and dependent components.
7. Execute the critical regression suite.
8. Recheck console and network behavior.
9. Recheck mobile and accessibility behavior.
10. Recheck data lineage.
11. Capture after screenshots.
12. Run a separate verifier that did not implement the change.

Use a maximum of three remediation rounds.

Require two consecutive independent live rounds with:

- No new CRITICAL finding.
- No new HIGH finding.
- No new MAJOR finding.
- No regression of a previously passing gate.

# 17. Release gates

## G0 — Authorization and identity

Pass only when target ownership, scope, repository, live URL, deployed SHA, and
Pages deployment are known.

## G1 — Requirement and claim coverage

Pass only when every claim and deliverable has a final status and evidence.

## G2 — Scientific and data provenance

Pass only when every current value has verified source lineage and no synthetic
or stale value is presented as current.

## G3 — Source and update automation

Pass only when live acquisition, validation, freshness, no-change behavior,
failure behavior, watchdog, and atomic publication are verified.

## G4 — Threshold and status integrity

Pass only when policies, exact boundaries, unclassified gaps, compatibility,
official status, GRD signal, and data quality are correct and separate.

## G5 — Core functionality

Pass only when every advertised tab, chart, map, table, download, tutorial, and
assistant mode works or has an approved honest unavailable state.

## G6 — Responsive and accessibility

Pass only when required browser/device profiles, reflow, overflow, keyboard,
focus, contrast, and alternatives pass.

## G7 — Security and privacy

Pass only when no CRITICAL or HIGH owned-surface security defect or public
secret remains.

## G8 — Documentation and code quality

Pass only when code, documentation, comments, examples, and production behavior
agree and no placeholder or hardcoded current value remains.

## G9 — Change, CI/CD, and deployment

Pass only when every candidate change is reviewed, required checks pass, the
correct artifact is deployed, and live SHA equals intended SHA.

## G10 — Independent live verification

Pass only after two consecutive quiet live-production rounds.

# Defect versus improvement

Record a defect when an approved requirement, scientific rule, documented
claim, or expected user behavior is violated.

Record an improvement when the existing behavior is valid but can be made
clearer, safer, faster, more maintainable, more accessible, or more useful.

Do not hide defects as optional improvements.

Classify defects:

- CRITICAL.
- HIGH.
- MAJOR.
- MODERATE.
- MINOR.

Classify improvements:

- P0 prevents likely failure.
- P1 high value.
- P2 useful.
- P3 optional.

# Testing and fixes

For each confirmed defect:

1. Preserve live evidence.
2. Create at least two root-cause hypotheses for major defects.
3. Run discriminating diagnostics.
4. Confirm the cause.
5. Search for the same pattern across the repository.
6. Write a failing regression test.
7. Confirm the Red state.
8. Compare at least two realistic fixes for CRITICAL, HIGH, or MAJOR defects.
9. Implement the smallest complete correction.
10. Run focused tests.
11. Run all affected tests.
12. Run the critical regression suite.
13. Update accurate documentation.
14. Commit the implementation and tests together.
15. Open or update a pull request.
16. Pass required checks and review.
17. Merge.
18. Deploy.
19. Verify the intended SHA is live.
20. Retest the defect and affected neighbors.
21. Obtain independent verification.
22. Close it only as VERIFIED_LIVE.

Use no more than three remediation rounds.

A test that passes only after retry is flaky and does not satisfy a critical
gate.
